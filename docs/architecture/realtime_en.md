# Realtime Channel

> 中文原文：[realtime.md](realtime.md)
>
> Status: Foundation layer implemented · Last updated: 2026-11-26

Morfa uses a single WebSocket connection to carry high-frequency requests, subscriptions, and server pushes. It is not a "giant request", but a **multiplexing protocol over a single connection**.

## Goals

- Keep high-frequency, low-latency, small-payload operations on a single realtime connection.
- Subscription data is pushed by the server instead of being polled.
- HTTP continues to carry one-off requests, files, sensitive operations, and the public API.
- Each business operation is implemented once, with HTTP / WebSocket sharing the same service.
- Reserve a unified channel for future canvas collaboration, Agent streaming output, notifications, and presence.

## Transport boundaries

| Scenario | Transport |
| --- | --- |
| Preference sync, notifications, presence, collaboration | WebSocket |
| Agent / model streaming events | WebSocket (planned) |
| Sign-in, registration, VCode | HTTP |
| File upload, download, export archive | HTTP |
| Public MCP JSON-RPC | HTTP |
| Password, VCode, API key, and other sensitive one-off operations | HTTP |

WebSocket is the realtime channel for the internal web client and **is not part of the public MCP protocol**. External MCP clients continue to use standard HTTP JSON-RPC at `POST /mcp`.

Agent streaming events (planned) reuse this channel; structured incremental payloads are planned to use XAIOP encoding. XAIOP only handles the payload and does not change the envelope or operation model defined on this page. See [XAIOP integration](../integrations/xaiop_en.md).

## Endpoint

```text
GET /api/realtime
Upgrade: websocket
Cookie: morfa_session=...
Origin: <same-origin>
```

Authentication currently uses the HttpOnly session cookie, and `Origin` is validated. The server releases subscriptions when the connection closes.

In the Vite development environment, `/api/realtime` is proxied to the API service with `ws: true`.

## Envelope

```json
{
  "v": 1,
  "id": "r_xxx",
  "type": "request",
  "module": "preferences",
  "action": "update",
  "payload": {
    "themeMode": "dark"
  },
  "meta": {
    "traceId": "trace_xxx",
    "ts": 1795639000000
  }
}
```

Response:

```json
{
  "v": 1,
  "id": "r_xxx",
  "type": "response",
  "ok": true,
  "payload": {
    "themeMode": "dark"
  }
}
```

Error:

```json
{
  "v": 1,
  "id": "r_xxx",
  "type": "response",
  "ok": false,
  "error": {
    "code": "PREFERENCE_THEME_INVALID",
    "message": "主题设置不正确"
  }
}
```

Server push:

```json
{
  "v": 1,
  "type": "event",
  "module": "preferences",
  "event": "changed",
  "payload": {
    "themeMode": "dark"
  },
  "seq": 12
}
```

Subscribe:

```json
{
  "v": 1,
  "type": "subscribe",
  "module": "preferences",
  "event": "changed"
}
```

Field constraints:

- `v`: protocol version, currently fixed at `1`
- `id`: correlates request and response; generated by the client
- `module` / `action`: routes to the operation registry
- `event`: server-push event name
- `payload`: business data
- `seq`: event sequence number, used for debugging and future reconnect recovery
- `meta`: only non-sensitive information such as traceId and time

## Server layering

```text
src/realtime/
├─ events.ts          # User-level domain event bus
├─ registry.ts        # module.action -> handler
├─ gateway.ts         # Connections, subscriptions, heartbeat, routing, push
├─ index.ts           # Singleton gateway
└─ operations/
   ├─ preferences.ts  # Preference read/write
   └─ index.ts        # Operation registration
```

The business layer only publishes domain events:

```text
updateUserPreferences()
  -> Write to SQLite
  -> publishRealtimeEvent({ module: "preferences", event: "changed" })
  -> Gateway finds user connections subscribed to the event
  -> Push event
```

When adding a realtime module:

1. Register `register(module, action, handler)` under `realtime/operations/`.
2. The handler calls an existing service and does not duplicate business logic.
3. When a push is needed, the service publishes `publishRealtimeEvent`.
4. The client calls `realtimeClient.request()` or `subscribe()`.

## Client

`apps/web/src/lib/realtime/client.ts` is a global singleton:

- One connection per tab
- Automatically assembles the `ws://` / `wss://` URL
- Request IDs, a pending map, timeouts, and cancellation
- Subscription registration and automatic resubscription after reconnect
- Exponential backoff with random jitter
- No reconnection after a manual sign-out
- Rejects all pending requests when the connection closes

`apps/web/src/lib/realtime/index.ts` provides wrappers for preferences and the MCP capability catalog, preferring WebSocket and falling back to one-off HTTP requests when the connection is unavailable. Public MCP capability calls are still exposed as HTTP JSON-RPC; the realtime channel only serves internal requests from the web client.

## Current integrations

| Module | Operations | Push |
| --- | --- | --- |
| `preferences` | `get` / `update` | `preferences.changed` |
| `mcp` | `capabilities.list` / `capabilities.get` | None yet |

Preference flow:

1. After sign-in, fetch a preference snapshot once over HTTP or WebSocket.
2. Subscribe to `preferences.changed`.
3. MCP, an HTTP PATCH, or another tab modifies preferences.
4. The server pushes to all online connections for that user over WebSocket.
5. The frontend applies the language and theme immediately.

Window-focus throttling and periodic polling are no longer used.

## Security and limits

- Maximum WebSocket message size is 256 KB.
- Heartbeat interval is 25 seconds; inactive connections are terminated automatically.
- The server validates `Origin`.
- Sign-out, password change, password reset, and account cancellation close the relevant user connections.
- Sensitive credentials are not pushed through realtime events.
- Public MCP still uses HTTP and does not expose the custom WebSocket envelope.
- Production should support WebSocket Upgrade at the reverse proxy layer and configure idle timeouts.
