# ADR 0003：主题与国际化作为一等能力

- 状态：已接受
- 日期：2026-11-25
- 决策者：项目维护者

## 背景

许多产品在后期才补上深色模式与多语言，导致：

- 颜色散落在组件中，深色模式靠覆盖样式，维护成本高；
- 文案硬编码，翻译时需全局搜索替换；
- 日期、数字格式不统一，英文界面出现中文标点；
- 主题切换闪烁，语言切换需要刷新。

Morfa 面向跨平台用户，主题与语言必须在架构和设计阶段就确定。

## 决策

1. **主题**
   - 支持 `system / light / dark` 三种模式，默认 `system`。
   - 所有颜色、间距、字体等通过设计令牌与 CSS Variables 提供，组件禁止硬编码颜色。
   - 在 `<head>` 中内联初始化脚本，首屏无闪烁。
   - 应用界面主题与用户设计内容主题解耦。

2. **国际化**
   - 默认 `zh-CN`，内置 `en-US`，资源按命名空间组织。
   - 所有用户可见文案通过 i18n 层获取，禁止在组件中硬编码。
   - 日期、数字、货币与相对时间使用 `Intl`。
   - 语言与主题偏好持久化，并同步 `<html lang>` 与 `data-theme`。

3. **工程约束**
   - 新增界面文案必须同时提交中英文资源。
   - 新增语义颜色令牌必须同时提供两套主题取值。
   - CI 校验语言键集合一致性与缺失键。
   - 主题与 i18n 的切换纳入 E2E 冒烟测试。

## 理由

- 主题与语言属于横切关注点，后补成本远高于前置设计。
- 令牌化与资源化让视觉调整和翻译可以独立于业务代码进行。
- 早期建立约束，可避免代码评审反复纠正硬编码问题。

## 后果

正面：

- 两套主题与两种语言从第一个可运行版本起即可验证。
- 视觉与文案变更集中管理，减少回归。
- 为后续增加语言或品牌主题打下基础。

负面 / 限制：

- 初期需要维护令牌与资源文件，短文案也要走 i18n。
- 翻译键对齐与截图评审增加少量流程成本。
- 需要处理首次加载、持久化与系统偏好变化等边界情况。

## 备选方案

| 方案 | 未采用原因 |
| --- | --- |
| 仅用 CSS 媒体查询，不提供手动切换 | 不满足用户显式控制需求，也不利于截图与测试 |
| 每个组件维护深色样式 | 分散且易遗漏，无法保证一致性 |
| 文案直接写中文，后续再抽取 | 会污染组件，后期替换成本高 |
| 引入第三方主题 / i18n 平台 | 早期无必要，增加外部依赖与数据外泄风险 |

## 后续动作

- M1 实现主题 Provider、令牌文件与初始化脚本。
- M1 接入 i18n，建立 `zh-CN` / `en-US` 资源与键校验脚本。
- 主题与语言切换纳入 Playwright 冒烟用例。
